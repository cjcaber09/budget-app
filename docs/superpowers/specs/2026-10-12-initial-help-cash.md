# Initial help and Cash setup

Four short modal steps introduce the app, the + entry menu, budgeting/reporting/bills/methods/sources, then Cash available now. Only a fresh owned snapshot with unset opening balance/baseline and loaded saved currency triggers automatic help on Overview. Zero is initialized. Later/Close suppresses prompts for this in-memory session; account changes/restarts/completed resets re-enable evaluation. Existing sheets and pending reset/deletion block presentation. Signed-in content remains available through loading/errors.

Settings has a compact circle-help icon and visible Need help? label in a shared fixed footer, with a 44px touch target and room for the + FAB. Manual Help permits reading offline; known initialized Cash ends with Done after three steps. Unknown Cash/settings show recovery before setup. The menu illustration consists of real cropped synthetic phone-web screenshots in light/dark WebP (about 7KB each), bundled locally. Matching accessible text carries all instructions. No bank connectivity or automated bill-payment claims.

The amount starts blank, accepts explicit zero, rejects negative/invalid/out-of-range amounts, and uses live thousands separators plus saved currency. Initialization establishes the existing baseline without creating income or double-deducting pre-baseline history. New migration0033 exposes initialize_cash_balance(uuid,text), with auth-derived ownership, account-active financial lock and Cash row lock. An initialized balance returns already_initialized without changing amount/baseline. The expected Cash ID rejects stale reset/account targets. The RPC identity fails safely on older servers; there is no ordinary-edit fallback.

Save requests use exact decimal strings and owner/method/outcome response validation. Busy guards reject duplicate submission. Failures retain the draft and require a fresh owned Cash snapshot before retry; initialized state finishes without a second write. Late responses cannot close a new owner's/reset's walkthrough. Successful writes refresh payment methods/dashboard/bills/reports. Passwords and permanent-delete acknowledgment already protect both account deletion and Clear records; deletion now uses the matching icon button and clears password/acknowledgment on cancellation/reopening. Server deletion/reset behavior is unchanged.

## Release freshness correction

The code4 APK's embedded app.manifest retained commitTime 2026-10-10T23:52:53.332Z while the published preview update is dated 2026-10-11T16:04:54.695Z. Expo's installed launcher chooses the newest compatible commitTime; the previous published code can therefore supersede the APK's corrected currency code. The source Overview remains reactive through useMoneyCents and passes its actual React Compiler USD-to-PHP regression.

withFreshEmbeddedUpdate config plugin makes createReleaseUpdatesResources run on every native release, regenerating the timestamp and asset list rather than retaining Gradle's stale output. The same change is applied to the ignored existing native checkout and is idempotently restored on prebuild. This does not publish or repair an already-installed APK. A new authorized release must verify embedded manifest freshness against the preview update before handoff.
